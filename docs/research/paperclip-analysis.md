### Overall verdict

Paperclip already contains most of the primitives the owner's loop needs: a typed task tree with atomic checkout, per-agent runtime/model configuration across all requested runtimes except omp, automatic session resume, reviewer/approver stages that are server-enforced for any adapter, queued human comments with interrupt, crash recovery, an attention inbox, a Telegram connector that routes to a single lead agent, per-company isolation, and an extension surface (plugins, external adapters, MCP, REST, CLI). What is usable as-is is the work graph, execution, review gates, cost ledger and human-attention surfaces; what needs configuration is almost everything that makes it behave as a "CTO talks, owner approves only deploys" system (policy stamping on every subtask by the lead, worktree isolation per project, concurrency limits, chat connector flag and webhook, watchdog attachment, routines for status digests, a gateway-routed deploy/delete gate). What needs building (core or plugin) is: a default execution policy so review is automatic, server-enforced evidence for the verifier, supervisor routing so stalls wake the lead instead of the board (and a kill/poke for live-but-hung runs on non-Codex adapters), a feed of significant autonomous decisions, merge orchestration for parallel executors, an omp adapter, and a shell-level gate for deploy/delete since CLI agents run with permissions skipped. The two dominant risks are scale and stability rather than missing features: roughly 1.35M source LOC (of which most is surface the owner will not use: cloud, voice, tool marketplace, pipelines) concentrated in monolithic files, a 61%-single-author history with about 150 commits per week, ~3,060 open issues (stall/recovery, Hermes adapter, memory/OOM, embedded-DB and upgrade regressions dominate), and a 3.5 GB RAM target that the default concurrency and open leak reports make risky. Forking core is expensive; extending through plugins, external adapters, instructions and REST is cheap.

## SECTION 3. Agent execution loop

### 3.1 Wake model: agents are not long-running
- Agents run in finite "heartbeats": start adapter, give prompt/context, run until exit/timeout/cancel, store result, exit (docs/agents-runtime.md section 1; doc/architecture/durable-continuation-scheduler.md first para: "Paperclip does not keep an agent process alive between turns").
- Invocation sources enum: `timer | assignment | on_demand | automation` (packages/shared/src/constants.ts:896 HEARTBEAT_INVOCATION_SOURCES). Finer-grained `wakeReason` strings ride in context (e.g. `issue_assigned`, `issue_comment_mentioned`, `issue_children_completed`, `execution_review_requested`, `execution_approval_requested`, `execution_changes_requested`, `source_scoped_recovery_action`, `missing_issue_comment`, `issue_blockers_resolved`, `issue_continuation_needed`, `transient_failure_retry`, `workspace_busy_retry`, `task_watchdog_stopped_subtree`; seen in server/src/services/heartbeat/queue.ts, retries.ts, doc/TASK-WATCHDOG.md, doc/ES).
- Concrete wake triggers verified:
  - Timer: per-agent `runtimeConfig.heartbeat.{enabled,intervalSec}`; DEFAULTS ARE OFF (`enabled` default false, `intervalSec` default 0) (server/src/services/heartbeat/queue.ts:395-397). Option `skipTimerWhenNoActionableWork`, `maxDailyRuns` exist (queue.ts:398-410). Scheduler tick every 30 s default (`HEARTBEAT_SCHEDULER_INTERVAL_MS`, min 10 s; doc/architecture/durable-continuation-scheduler.md).
  - Assignment: `wakeOnAssignment`/`wakeOnDemand` on by default (server/src/services/heartbeat-policy.ts: `asBoolean(..., true)`).
  - Comment: top-level board/user comment on an agent-assigned non-terminal issue wakes the assignee (doc/ES "Comment and document activity wake sources"). Document/annotation comments do NOT wake. @-mentions and agent-to-agent comments do NOT wake or assign ("Agent names and structured @-mentions are context, not assignment or wake requests", doc/ES "Comment interrupts and ownership handoffs"); lateral work goes through "courier" child issues (doc/ES 6).
  - Execution-policy stage entry wakes the reviewer/approver (`execution_review_requested`, `execution_approval_requested`), changes-requested wakes the executor (`execution_changes_requested`).
  - Child done: `issue_children_completed` wakes parent; blockers resolved: `issue_blockers_resolved` wakes dependent (doc/ES 9.2, 6).
  - Approval/interaction answered: `PAPERCLIP_APPROVAL_ID` wake (docs/guides/agent-developer/heartbeat-protocol.md step 2); issue-thread interaction `continuationPolicy: wake_assignee` (doc/TASK-WATCHDOG.md last section).
  - Monitors: one-shot `executionPolicy.monitor.nextCheckAt` wakes assignee for a bounded future check (doc/ES "Issue monitors"; server/src/services/issue-monitors.ts).
  - Routines (cron-ish, packages/db/src/schema/routines.ts, docs/api/routines.md) create issues/wakes (not deep-read; UNVERIFIED details).
  - Recovery/watchdog wakes (see 3.8).
- Coalescing: if an agent is already running, new wakeups are merged, not duplicated (docs/agents-runtime.md section 2). One active run per issue ("Single execution invariant", docs/guides/execution-policy.md Design Principle 5).

### 3.2 Prompt and context an agent receives
- Prompt = server-built "wake prompt" + agent `promptTemplate` + task context markdown. Default template is tiny: `"You are agent {{agent.id}} ({{agent.name}})."` + connection-intent guidance (packages/adapter-utils/src/server-utils.ts:212-216). Operational procedure lives in the harness-delivered `paperclip` SKILL (comment at server-utils.ts:218-220; skills/paperclip/SKILL.md ~900+ lines). `bootstrapPromptTemplate` deprecated in favor of "managed instructions bundle" (docs/agents-runtime.md 3.4).
- `renderPaperclipWakePrompt` (server-utils.ts:2243) composes: wake payload (reason, issue summary, batch of wake comments, execution stage info, recovery instruction, continuation envelope, resume delta), assigned connector skill instructions, connection instructions. Recovery-specific text per cause e.g. `process_lost`: "Your previous run on this issue was lost ... resume from durable progress; don't redo completed steps" (server-utils.ts ~2300). Watchdog gets `WATCHDOG_DEFAULT_MANDATE` (server-utils.ts:222-244).
- Env passed to the process (names only, server-utils.ts grep): `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY`, `PAPERCLIP_AGENT_ID`, `PAPERCLIP_COMPANY_ID`, `PAPERCLIP_TASK_ID`, `PAPERCLIP_WAKE_REASONS`, `PAPERCLIP_WAKE_PAYLOAD_JSON`, `PAPERCLIP_WORKSPACE_{CWD,BRANCH,ID,SOURCE,STRATEGY,WORKTREE_PATH,REPO_URL,REPO_REF}`, `PAPERCLIP_WORKSPACES_JSON`, `PAPERCLIP_RUNTIME_API_URL`, `PAPERCLIP_RUNTIME_TOOLS_*` (MCP URL, token).

### 3.3 How agents read/write back
- Primary: REST API `/api/...` with a per-run signed token (agent JWT or API key) + header `X-Paperclip-Run-Id` on mutations (docs/guides/agent-developer/heartbeat-protocol.md steps 1-8; skills/paperclip/SKILL.md). Helper script `skills/paperclip/scripts/paperclip-issue-update.sh` verifies HTTP status.
- Skill delivery: `paperclip` skill auto-injected to skill-capable legacy adapters; `complain` + `suggestion-box` too (doc/agent-commentary.md).
- Native runs: typed tools (`call_api`, `create_task`, `set_dependencies`, `set_task_monitor`, `paperclip_finish`, ...) bound to run authority, no API credential in the process (doc/ES section 7, "set_task_monitor"; doc/runner-api-tools.md; doc/ES "Completion tools and final answers").
- MCP: `packages/mcp-server`, doc/TASKS-mcp.md, doc/MCP-RUNTIME-OPERATIONS.md (runtime-tools MCP URL env above). Detail not read.
- Heartbeat protocol (heartbeat-protocol.md): identity -> approval follow-up -> inbox (`GET /api/companies/{c}/issues?assigneeAgentId=..&status=todo,in_progress,in_review,blocked`) -> pick work -> `POST /api/issues/{id}/checkout` -> read issue+comments -> work -> `PATCH` status with `comment` -> delegate via child issues (always set `parentId`, `goalId`).

### 3.4 Task checkout / locking
- `checkoutRunId` (ownership lock for current run) vs `executionRunId` (currently live run) on issues (doc/ES section 5). Checkout required to move to agent-owned `in_progress`; `409` = real live owner/ gate; agents told "Never retry a 409" (heartbeat-protocol.md Critical Rules). Locks compare-and-clear on run terminal; stale locks self-heal; admission under per-issue lock (doc/ES 5). Single assignee invariant (assigneeAgentId XOR assigneeUserId).

### 3.8 Stall / waiting-for-input / crash handling, recovery, watchdogs
Layers actually present (verified in doc/ES sections 8-13 and doc/TASK-WATCHDOG.md):
1. Startup + periodic reconciliation (every scheduler tick, 30 s): reap orphaned `running` runs, resume persisted `queued` runs, `reconcileStrandedAssignedIssues()`, scan silent runs (doc/ES 10; durable-continuation-scheduler.md "When it runs").
2. Stranded assigned `todo`/`in_progress`: queue ONE automatic recovery wake to the SAME assignee; if that also dies, issue -> `blocked` + open a board-owned explicit recovery action; assignee unchanged, "no substitute agent is woken" (doc/ES 9.1, 9.2).
3. Deliberate-wait without target: 5 disposition-repair attempts (0, 60, 120, 240, 480 s, 10% jitter) then one board-owned recovery action (doc/ES 9.2).
4. Liveness contract: a non-terminal agent-owned issue must always have an action path (active run, queued wake, typed review participant, pending interaction/approval, monitor, human owner, blocker chain, open recovery action); `blocked` requires blockers / pending interaction / structured `{owner, action}` unblock descriptor, prose-only blocked is rejected or auto-classified `needs_attention` (doc/ES 3 `blocked`, 8). Recovery action kinds: `missing_disposition, deliberate_wait_without_target, stranded_assigned_issue, workspace_validation, configuration_validation, active_run_watchdog, issue_graph_liveness`; owner types `agent|user|board|system` (constants.ts:377-404). Review-path recovery: participant run ends with no decision => one bounded recovery wake, then blocked/recovery (doc/ES 8 `in_review`; server/src/services/recovery/review-path-recovery.ts).
5. Silent active-run watchdog: classifies output silence `suspicious` after 5 min, `critical` after 15 min; this is INFORMATIONAL ONLY: "do not ... wake an agent, cancel the active process, or change the run" (doc/ES 12). Board can snooze/continue/dismiss (table heartbeat_run_watchdog_decisions). So a live-but-hung run is NOT auto-killed or auto-poked except Codex inactivity monitor and `timeoutSec`.
6. Task watchdog (opt-in per issue, doc/TASK-WATCHDOG.md): attach an agent to an issue; when the whole subtree has stopped (done/cancelled/blocked/in_review/waiting) with no live path and the stop fingerprint is new, a child review task is created/reopened and the watchdog agent is woken (`task_watchdog_stopped_subtree`) with mandate to verify stop claims against evidence (comments, docs, work products, screenshots, tests) and restore a live path. Cannot bypass typed execution-policy reviewers, cannot approve spend/hiring, scope-limited to the subtree (server/src/services/task-watchdogs.ts 1815 lines; task-watchdog-scope.ts; API `GET/PUT/DELETE /api/issues/:id/watchdog`). Fires at server startup, end of each heartbeat cycle, and after mutations.
7. Stalled-review UI decisions: board can `approve | request_changes | send_back` on a stalled `in_review` issue (server/src/services/stalled-review-decisions.ts; types/issue.ts:512).
8. "Automatic productivity reviews are retired" (doc/ES 10) - there is no automatic nag on slow progress.
9. Waiting for human input: pending issue-thread interaction (`request_confirmation`, `ask_user_questions`, `suggest_tasks`) is a valid wait; ordinary question comments become "historical" when a newer human message appears (doc/ES 3 `blocked`). Expiry of an unanswered prompt: UNVERIFIED (no timeout found in docs read; monitors/watchdog are the only time-based escalations).

### 3.9 Mid-run user messages (fit-gap 2) - mechanics
- New comment while a run is active is queued ("deferred" wake with ordered comment ids) in a per-issue queue: server/src/services/issue-queued-comment-queue.ts, routes `GET/PATCH/DELETE /issues/:id/queued-comments`, `/order`, `/interrupt`, `/:commentId/steer` (server/src/routes/issues.ts:16206-16642). Queue revision hash guards edits.
- Legacy runner: Interrupt = stop active run then deliver queued messages as a fresh turn (resumes saved session); Steer unsupported (decision `unsupported`/`temporarily_unavailable` in `decideQueuedCommentQueueSteering`, issue-queued-comment-queue.ts:~100-208). Default non-interrupt path = message waits and is delivered after the run finishes (doc/ES "Delivering queued messages after a legacy run stops", "Responses submitted during an active run").
- Native runner: same-turn Steer (provider acknowledgement is the delivery receipt) (doc/ES 1519-1560).
- Composer Stop = pause hold on task/subtree; comments rejected `409` while hold active; run-level Stop leaves queue and session so a later comment continues same session (doc/composer-stop.md).
- Board comment may carry an interrupt and/or an assignee change; mentions do nothing (doc/ES "Comment interrupts and ownership handoffs").

## Review / approval execution policy (central to fit-gap 1, 4, 8)

(1..50, null=default 3) }` (validators/issue.ts:436-451). `mode:"auto"` semantics: UNVERIFIED (enum only; no `policy.mode` branching found in server code by grep).
- Stage: `{ id, type: "review"|"approval", approvalsNeeded: 1 (literal; multi-approval unsupported), participants[] }`; participant = `{type:"agent", agentId}` or `{type:"user", userId}`. Stage types only `review` and `approval`; both behave the same except the auto-skip rule (`canAutoSkipPendingStage` skips a `review` stage when all participants equal the executor and status is done, issue-execution-policy.ts:~652).
- State: `idle|pending|changes_requested|completed`, `currentStageId/Index/Type`, `currentParticipant`, `returnAssignee`, `reviewRequest{instructions<=20000}`, `completedStageIds`, `lastDecisionId/Outcome`, `changesRequestedCount`, `monitor`.

Transition engine (`applyIssueExecutionStageTransition`, issue-execution-policy.ts ~668-1100), enforced inside `PATCH /api/issues/:id`:
1. Executor sets `status:"done"` or `"in_review"`: server intercepts, sets `in_review`, picks participant of next pending stage (`selectStageParticipant`, preferring requested assignee and EXCLUDING the original executor/returnAssignee - no self-review), reassigns issue to that participant, stores `returnAssignee`, wakes participant (`execution_review_requested`/`execution_approval_requested`).
2. Active participant PATCHes `done` + `comment` in the SAME request (separate prior comment does not count; error text STAGE_DECISION_COMMENT_HINT) => decision row `approved`; advances to next stage or `executionState.completed` and real `done`.
3. Participant PATCHes any other status (typically `in_progress`) + comment => `changes_requested`, issue returns to `returnAssignee` as `in_progress`, executor woken; on resubmit it returns to SAME stage.
4. Only `currentParticipant` may advance; others get 422 ("Only the active reviewer or approver can advance the current execution stage"). Board users can override (`allowBoardOverride`), which dissolves/re-pends the stage.
5. Round cap: agent-initiated changes-requested rounds count; at `maxReviewRounds` (DEFAULT_MAX_REVIEW_ROUNDS = 3, :63) the stage stays pending but is HANDED TO THE RESPONSIBLE HUMAN (`reviewEscalationUserId(issue)`: responsibleUserId/createdByUserId) instead of bouncing to executor; human decisions reset the counter. IMPORTANT for the owner: default will pull the human in after 3 agent ping-pong rounds unless `maxReviewRounds` is raised (max 50) or no human is resolvable.
6. Review-path liveness: participant run that ends with stage still pending and no decision => one bounded recovery wake, then explicit blocked/recovery action (doc/ES 8 `in_review`).
7. Native completion review (different mechanism, native runner only): saved review card + durable reviewer wake; accepting last required review marks child Done; see doc/architecture/native-status-arbitration.md "Agent review handoff".

Orthogonal "review policy" for interaction cards (issue-review-policy.ts): `reviewPolicy` `anyone | human_only | not_creator` decides who may resolve a review-verdict interaction; `not_creator` requires someone other than the writer who moved the issue to in_review; errors `review_policy_denied`. Interaction resolver policy defaults to `anyone` (includes the creating agent) unless creator sets `not_creator`/`human_only` (doc/ES 10 "Issue-thread interaction resolution"). Lets a plan confirmation be accepted by an agent.

Where policy comes from: set on issue create/update by whoever creates the issue (UI New Issue dialog "Reviewer"/"Approver" buttons; API `executionPolicy`; agents can set it, routes/issues.ts:3959-4000 `resolveCreatedIssueExecutionPolicy`; low-trust agents can only narrow). I found NO company-level or project-level default execution policy or template (grep for `defaultExecutionPolicy` empty; projects only have `executionWorkspacePolicy`, validators/project.ts:24-40) => UNVERIFIED but likely absent: every issue must be stamped with stages by the creator (CTO agent instructions) or a routine/plugin.

Role -> model mapping: participants are AGENTS; each agent has its own `adapterType` + `adapterConfig` (model, effort, etc.). So "reviewer on Sonnet low effort" = a separate reviewer agent configured so. Additionally an issue can carry `assigneeAdapterOverrides {adapterConfig, useProjectWorkspace}` (validators/issue.ts:~299) to override the assignee's adapter config for that issue (e.g. model), merged in `buildExecutionWorkspaceAdapterConfig` (server/src/services/execution-workspace-policy.ts:~430). ### Outbound (status/question delivery)

## (5) HIERARCHY AND DELEGATION
---------------------------------------------------------------------

Org chart: agents.reports_to strict tree; validated by ensureManager in lib/agent-records (called from prepareAgentHire, services/agent-hiring.ts) and by assignability checks that walk the ancestor chain and refuse work for agents with a terminated/missing/cross-company/cyclic ancestor (services/agent-assignability.ts, reasons ancestor_terminated, ancestor_missing, ancestor_cycle, ancestor_depth_exceeded). `GET /api/agents/me` returns chainOfCommand (routes/agents.ts ~L1298).

Can agents create subtasks and assign to reports? YES.
- Instruction-level: onboarding-assets/ceo/HEARTBEAT.md section 6 "Delegation": POST /api/companies/{id}/issues with parentId and goalId; "Assign work to the right agent".
- Permission-level (doc/agent-permission-defaults.md): every new standard agent gets direct grants tasks:assign, tasks:assign_scope (scope = its own reporting subtree, lib/agent-permissions.ts L25 `subtreeRootAgentId`), tasks:manage_active_checkouts, agents:configure, agents:suggest-changes, skills:*, tools:*, inbox:manage. So by default ANY agent (not only managers) can create and assign tasks within its subtree; "same-company agents ... assign tasks under the assignment policy".
- Low-trust agents may only create self-assigned tasks and subtasks of own tasks (doc/LOW-TRUST-PRESETS.md).
- Single assignee; atomic checkout; one active run per issue (execution lock) so a parent cannot be double-run.
- Parent wakes: PAPERCLIP_WAKE_REASON=issue_children_completed when all direct children reach done/cancelled; issue_blockers_resolved for blockers (skills/paperclip/SKILL.md ~L296-314).

Can agents hire/create agents? YES, by default.
- New standard agents have `canCreateAgents: true` (legacy flag path for `agents:create`; agent-permission-defaults.md; lib/agent-permissions.ts L73). `agents:create` is NOT in the default grant rows.
- Path: POST /api/companies/:id/agent-hires (routes/agents.ts ~L4300-4400): if company.requireBoardApprovalForNewAgents -> agent created with status pending_approval + a hire_agent approval; else status idle immediately. How a manager accepts/rejects/reworks a subordinate's result:
- Mechanism = per-issue `execution_policy` stages (doc docs/guides/execution-policy.md; services/issue-execution-policy.ts, 1227 lines). Stages type review|approval, participants agents or users; runtime intercepts executor's `status: done` -> sets in_review, reassigns to first eligible participant (excludes original executor), executionState pending. Reviewer PATCHes `status: done` + `comment` = approve (records issue_execution_decisions row; advances or completes); PATCHes any non-done status (typically in_progress) + comment = request changes: runtime sets status in_progress, reassigns back to returnAssignee, state changes_requested; same reviewer re-reviews on resubmit. Comment is mandatory in the SAME PATCH (guard). Non-participants get 422. Board can override (allowBoardOverride).
- Who sets the policy? Whoever creates/updates the issue (API field executionPolicy; UI New Issue dialog has Reviewer/Approver pickers). Nothing applies a policy automatically: a lead agent must put `executionPolicy` on each subtask it creates (instruction/convention), or a default must be injected (UNVERIFIED whether a company/project-level default policy exists; grep of schema found no such column; services/execution-policy-bootstrap.ts exists - not read).
- review_policy (issues.review_policy anyone|not_creator|human_only; services/issue-review-policy.ts) constrains WHO may give the verdict on in_review (not_creator = someone other than the actor who moved it to in_review; human_only = authenticated user).
- Alternative acceptance path: parent's assignee is woken on issue_children_completed and can reopen/comment/create follow-ups (instruction-driven, not enforced).
- Task watchdog (issue_watchdogs, doc/TASK-WATCHDOG.md): an agent assigned to verify a stopped subtree and restore live paths; verification-shaped ("declaring done without proof", "in_review with no real reviewer").

### 14. Separate companies with isolated agents/projects/secrets - READY at the data/API level, with shared-host caveats

Company-level "revenue/expense" is explicitly out of V1 (SPEC-implementation 5.2).
- Verdict: READY for corporate vs personal separation as two companies in one instance; if the owner wants hard isolation (different OS user / secrets key / blast radius) run two instances (Paperclip is designed single-tenant per instance).

### Fit-gap 16: runs on 4 vCPU / 3.5 GB behind nginx on loopback port
Verdict: **CONFIG, with a RISK on memory**.
- Works: loopback bind + `TRUST_PROXY` + `PAPERCLIP_PUBLIC_URL` + dedicated hostname + nginx WebSocket upgrade; run as systemd user service via `paperclipai service install`; use `authenticated/private` (login) not `local_trusted` since traffic arrives via proxy; Node 24 required (check VPS node version; managed installer can bootstrap).
- Risk: embedded PG + Node server + N plugin workers + per-run CLI processes in 3.5 GB; open leak #15815 and OOM-class issues; no built-in memory ceiling. Mitigations (reporter used): systemd `MemoryHigh` drop-in, nightly restart, lower `maxConcurrentRuns`, external/lighter Postgres via `DATABASE_URL`, fewer plugins, avoid Docker build on box.
- Caveat: no Docker image size/idle RSS numbers published; measure on target before committing.

# Coupling verdicts summary

Question: can each feature be removed or disabled without breaking the core loop (agent wake -> task -> run -> report -> review)? Evidence is in Part C (coupling map) and Part D (flags).

| Feature group | Aimed at | Verdict | Evidence |
|---|---|---|---|
| Paperclip Cloud, customer-success, cloud warm-standby/runner ingress | hosted multi-tenant product | Inert when self-hosted, NOT cleanly removable | `cloud-instance` imported by ~18 non-test files incl. `middleware/auth.ts`, `routes/agents.ts`, `services/companies.ts`; env-driven |
| Company templates/portability, teams-catalog, ClipHub | zero-human company packs | Disable easily; but teams-catalog is also how the CTO/QA/coder packs are installed | `company_transfer_runs` is a leaf table; ClipHub is spec only (not built) |

| Status cards, summary slots, fast responses, decision models | exec summaries, LLM plumbing | Off by default; ignorable | leaf tables; flags default false |
| Chat connectors (Slack, Teams, Discord, GitHub, email, voice, iMessage, Telegram) | external front doors | Not entangled with the kernel (issues.conversation_* columns only); keep Telegram, ignore the rest | `enableChatConnectors` default false |

Richest mid-run features (Steer, evidence) live only here, but maturity is UNVERIFIED (ADR "Proposed"; Rust binary needed) | schema island (`completion_contracts`, `work_assessments`, `status_decisions`); `enableNativeRunner` default true but "onboarding remains on legacy adapters" |
| Plugins framework | extensibility | Keep (it is the PLUGIN extension point); ~16 `plugin_*` tables, one forked worker per plugin | `plugin-worker-manager.ts` |

| Invites, join_requests, multi-human RBAC, onboarding seed | teams of humans, new-company wizard | Ignorable for a solo owner | leaf-ish tables |
| Core loop: companies, agents (+reports_to), issues (+relations, comments, documents, work products, execution policy), heartbeat runs/wakeups, approvals/interactions, activity log, secrets, projects/workspaces | the dev-team loop | Cannot be removed | ~25 of ~281 tables |

Structural observation: the schema layer is clean (peripheral tables are leaves; no core table references them), but the code layer is not. Roughly all routes are mounted unconditionally and flags are enforced inside handlers or only in the UI, and the monolithic files (`issues.ts`, `heartbeat.ts`, `routes/agents.ts`, `routes/issues.ts`) import cloud, native-runtime, chat and plugin hooks. "Removal" in practice means leaving features off by default, not deleting code; forking core is expensive.
